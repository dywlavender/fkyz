# Rule Engine v4

标准正文中的规则必须是已选定、可执行、可验证的确定口径，不是歧义清单。

## Rule Level

所有进入标准正文的业务规则统一使用：

| Level | 含义 |
|---|---|
| hard | 已选定、可执行、必须遵守并可验证的标准口径 |

不得把 `unclear`、`suggestion` 或“待确认后再定”写成主链规则。

## Basis Type

| basis_type | 含义 |
|---|---|
| requirement | 需求直接明确 |
| api_doc | 接口文档直接明确 |
| public_rule | 公共业务规则直接明确 |
| deterministic_inference | 可由输入唯一推导 |
| selected_interpretation | 存在多种实现时已选择的最可能口径 |

## Rule JSON Contract

每条规则必须包含：

- `rule_id`
- `dimension_ref`
- `source_section`
- `standard_level`，固定为 `hard`
- `basis_type`
- `basis_text`
- `evidence_ids`
- `selection_reason`，非选定解释时为空字符串
- `content`

`basis_type = selected_interpretation` 时，必须引用 `SEL-xxx` 并提供非空 `selection_reason`。

# Evidence Engine v4

Evidence ID 按来源类型固定：

| Evidence 前缀 | 来源类型 |
|---|---|
| REQ | 需求内容 |
| API | 接口文档 |
| PUB | 公共业务知识规则 |
| INF | 确定性推导 |
| SEL | 选定解释 |

排序规则：REQ、API、PUB、INF、SEL，同类型按原文或选择顺序编号。

每条 hard 规则必须引用至少一个 Evidence ID。

使用 `SEL-xxx` 时，必须在「选定解释」章节写明原始歧义、选定口径和选择理由。选择理由应说明为什么该方案最贴近需求语义和可用接口字段，不能只写“根据经验”。

---

# Freeze Rule

本阶段已冻结的输入、证据和规则集合不得在最终输出时临时扩充或改写。阶段专用冻结对象以本阶段规则为准。

---

# Deterministic Output v4

相同输入必须输出相同章节、相同对象顺序和相同判定口径。具体章节、编号和对象顺序以本阶段专用规则为准。

---

# Hallucination Guard

以下内容如果没有来自本阶段允许使用的输入或规则材料的明确依据，一律不得新增：

1. 新字段
2. 新接口
3. 新接口调用步骤
4. 新过滤条件
5. 新状态码
6. 新成功码
7. 新枚举值
8. 新默认值
9. 新兜底分支
10. 新时间窗口
11. 新边界条件
12. 新单位换算
13. 新精度
14. 新四舍五入方式
15. 新排序规则
16. 新去重规则
17. 新取最新/取第一条规则
18. 新分组字段
19. 新条件分支
20. 新业务规则
21. 新 Java 实现约束
22. 不改变字段值或加工结果的重复解析、同格式转换、同粒度转换

处理规则：

- 有明确依据：写入对应规则，并引用 Evidence ID。
- 完全没有输入依据的内容：不得新增。
- 只是工程实现建议且不影响加工结果：不写入标准。
- 无业务效果的操作，即使技术上可以执行，也不得包装成 hard 规则、确定性推导或选定解释。
- 仅格式名称、符号或书写方式不同，但数据组成、排列顺序和粒度相同，不构成格式转换依据；不得使用“规范化”等模糊措辞制造实际不存在的转换。

# Standard Generation Contract v4

本阶段只生成唯一、最可能、可直接执行的标准加工规范。

## 冻结对象

| 冻结对象 | 生成状态 | 冻结后限制 |
|---|---|---|
| INPUT_SET | STATE0 | 不得新增用户未提供的输入 |
| PUBLIC_RULE_SET | STATE1 | 不得新增公共规则 |
| API_DOC_SET | STATE2 | 不得新增接口文档 |
| FIELD_SET | STATE3 | 不得新增字段 |
| EVIDENCE_SET | STATE4 | 不得新增证据 |
| STANDARD_RULE_SET | STATE4 | 不得新增标准规则 |

冻结后如需增加字段、规则或证据，必须回到对应生成状态重新选择并冻结，不得在最终正文中临时补充。

## 章节顺序

1. `# 标准加工规范`
2. `## 输入解析`
3. `## 因子加工输入字段`
4. `## 字段溯源`
5. `## 过滤条件`
6. `## 列表/数组字段处理`
7. `## 计算逻辑`
8. `## 默认值兜底策略`
9. `## 比率/衍生因子计算`
10. `## 条件分支逻辑`
11. `## 选定解释`

规则编号固定使用 D1-D6、D8-D9；D6 之后直接使用 D8、D9。选定解释使用 SEL-001 起连续编号。

原始材料存在多个、但均由现有需求和接口字段支持的加工解释时，必须选择最可能的一种，登记为 `selected_interpretation`，不得发明新字段或新业务条件。不得输出主链“未明确”“待确认”“建议口径”或多套候选方案。

## 必要要素缺失

生成标准前必须确认需求中直接参与过滤、比较、聚合、计算或条件分支的每个必要业务操作数，都能映射到指定接口文档中的叶子字段。

如果任一必要业务操作数无法映射，输出且只输出：

`缺少要素：【接口字段：业务概念】`

此时不得继续生成标准正文，不得用类型相同、单位相同、字段唯一或技术上可执行作为替代映射依据，也不得通过 `selected_interpretation` 将不同业务概念合并到同一字段。

# Selected Interpretation

原始材料存在多个可能实现时，不得停止在“未明确”状态。Phase 1 必须选定最可能的一套可执行口径，并登记：

| 选择编号 | 触发位置 | 原始歧义 | 选定口径 | 选择理由 | 证据锚点 |
|---|---|---|---|---|---|

选择编号使用 `SEL-001`、`SEL-002`。相关标准规则必须引用对应 SEL 编号，且仍统一标记为 `hard`。

`selected_interpretation` 只能在多个均由当前需求、指定接口字段或公共规则支持的候选方案中选择，不得用于补齐缺失的必要业务要素。必须同时满足：

1. 每个候选方案使用的接口、叶子字段、业务操作数和条件均已存在于冻结输入。
2. 字段类型、单位或数据粒度相同，只能证明技术上可比较，不能证明业务概念相同。
3. 需求中的两个不同业务操作数不得映射为同一个字段，除非需求或接口文档明确说明二者同义或共用该字段。
4. 必要业务操作数无法映射到指定接口字段时，必须按必要要素缺失处理，不得选择类型最接近或当前唯一的字段代替。
5. 不得生成恒真、恒假或失去原需求业务含义的表达式来满足“唯一可执行”要求，例如无依据地把两个比较操作数映射为同一字段。

如果不存在选定解释，保留表头并在表格后写「无」。
